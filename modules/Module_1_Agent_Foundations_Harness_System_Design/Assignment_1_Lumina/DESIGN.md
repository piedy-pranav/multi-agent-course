# DESIGN.md — LUMINA

## Components

LUMINA is split into a React browser client, a public Express gateway, a private Express agent service, MongoDB Atlas, external LLM/search providers, and a document-ingestion worker. The React UI is the user-facing client and consumes the fixed HTTP/SSE contract from `packages/contract`. The gateway is the only backend service exposed to the browser; it handles browser-facing concerns and proxies requests to the agent service. The agent service owns the quick/deep agent loop, tool execution, memory, retrieval, citation construction, cost accounting, and run logging. MongoDB Atlas stores authoritative application state including threads, messages, memories, documents, chunks, usage/cap records, and jobs; it also provides Atlas Vector Search. Search results are cached in a two-tier cache consisting of an in-process LRU and the MongoDB `searchCache` collection with TTL expiry. Document ingestion is represented by the MongoDB `jobs` collection and processed outside the request path by a worker that parses, chunks, embeds, and indexes uploaded files. Run logs record each request's ordered tool calls, termination reason, latency, token usage, and cost for the benchmark and quality gates. The provided benchmark, eval, and quality code are outside the serving path and act as acceptance tests for the runtime system.

## Responsibilities

The React client may render state, send API requests, upload files, and consume SSE events, but it may not hold provider credentials, access MongoDB, or call LLM/search providers directly. The gateway is the only service allowed to talk directly to the browser; it owns CORS, `X-User-Id` enforcement, request IDs, request logging, Zod validation using the shared contract, general per-user rate limiting, SSE pass-through, and static UI serving. It does not decide how a question is researched and does not hold LLM or search-provider keys. The agent service is the only component allowed to hold provider secrets and make LLM, search, embedding, and retrieval decisions. It owns the bounded agent loops (quick: 8 tool calls/90 s; deep: 24 tool calls/240 s), tool traces, citations, memory tools, document retrieval, cost accounting, and the per-user deep-search daily cap, because that cap must be enforced next to the component that can incur the spend. The worker is the only component that performs long-running document indexing work; it claims pending jobs atomically and changes a document to `indexed` only after parsing, chunking, embedding, storage, and a successful read-your-write vector-search probe. `packages/contract` defines shared request, response, and SSE shapes, but does not implement runtime behavior; the backend services are responsible for satisfying that contract.

## Communication

The browser communicates with the gateway over HTTP, and `POST /threads/{id}/ask` remains open as an SSE stream so `trace`, `sources`, `token`, and `done` events can arrive incrementally; deep requests additionally emit `plan` before retrieval. The gateway communicates with the agent service over HTTP and forwards the agent's SSE stream without buffering so the browser receives events as they are produced. The agent service calls the LLM, embedding, and web-search providers over HTTPS and talks to MongoDB through the MongoDB driver. Document ingestion is asynchronous rather than request/response: an upload stores the file and metadata, inserts a pending MongoDB job, and returns `202 Accepted` quickly; the worker later polls and atomically claims the job. Failures are surfaced rather than converted into plausible answers: invalid client input produces a 4xx response, rate/deep-cap violations produce `429`, and an unavailable agent or upstream provider produces `502`; tool failures also appear as `trace` events with `ok: false`, and the run is logged with `terminated: "error"`. If an upstream dependency fails after an SSE stream has started, the current run is treated as failed and the stream terminates rather than being silently replayed, because transparent retries could duplicate tool calls, costs, memory writes, or citations. Worker failures occur after the original `202` request has ended, so they are represented persistently by failed job/document state instead of an HTTP response to the original upload.

## State

Authoritative persistent state lives in MongoDB Atlas. Threads and messages provide conversation memory within a thread; the `memories` collection stores explicit long-term user facts/preferences created through `save_memory` and exposed through the memory API; documents and their source files are authoritative user content; chunks and embeddings are derived retrieval state used for RAG; jobs represent asynchronous ingestion state; and usage/cap data determines whether deep search is still allowed. During an individual agent run, transient state such as the current plan, retrieved pages, tool observations, citation map, tool-call count, and accumulated source set may remain in process memory and can be discarded after the run. Search caches are non-authoritative: both the in-process LRU and MongoDB `searchCache` can be deleted without losing user data, although doing so increases latency and provider cost; time-sensitive queries should bypass this cache. Vector indexing is eventually consistent, so writing chunks does not mean a document is immediately searchable. A document remains in a non-indexed processing state until the worker can query Atlas Vector Search and observe data from that document; only after this read-your-write probe succeeds is its status changed to `indexed`. Run logs are durable evidence of what the agent actually did and are used to reconcile `/stats` and evaluate correctness, cost, and termination behavior.

## Trade-offs

The first trade-off is using two Express services instead of one: separating the public gateway from the private agent adds an extra network hop and more deployment/debugging work, but keeps provider secrets and spending controls away from the browser-facing boundary and lets HTTP concerns evolve independently from agent orchestration. Second, MongoDB Atlas is used for operational data, vector retrieval, TTL search cache, and the jobs queue instead of introducing specialist systems such as Redis, SQS/RabbitMQ, and a dedicated vector database. This reduces infrastructure and keeps document metadata, chunks, and citations close together, at the cost of polling-based jobs, eventual vector-index consistency, and fewer specialized queue/vector features. Third, SSE is used instead of WebSockets because the main real-time pattern is one request followed by server-to-browser plan/trace/source/token events; this is simpler and works naturally with HTTP, but it would be less suitable if LUMINA later required rich bidirectional realtime interactions. Fourth, the initial deep-search implementation should use one orchestrator that plans sub-questions and researches them with tools, optionally running independent I/O concurrently, rather than requiring multiple communicating agents. This is cheaper, easier to trace, and simplifies citation merging and cap enforcement, but gives up context isolation and some parallelism that isolated subagents could provide. The decision I am least certain about is using MongoDB itself as the job queue: it is appropriate for the assignment scale and avoids another service, but a production system with high ingestion volume or stronger retry/dead-letter requirements would likely benefit from a dedicated queue.
